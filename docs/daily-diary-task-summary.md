# 每日日记任务总结报告

## 1. 项目概况

“每日日记”是一套由 Hermes Agent 定时执行的长期写作与归档流程。它不只是每天生成一篇文字，而是把当天真实互动、经过筛选的新闻、一本值得深入讨论的书，以及 AI 自己的观察和感受，组织成一封有温度的夜间来信。

- **运行方式**：每天 22:00 由 cron 触发
- **日记格式**：Markdown，文件名为 `YYYY-MM-DD.md`
- **本地唯一存档**：`~/.hermes/memory/daily-diary/`
- **公开备份**：本仓库的 `diaries/`
- **已公开备份**：35 篇
- **时间范围**：2026-04-23 至 2026-08-06
- **当前状态**：任务已于 2026-08-06 暂停，不再自动执行；历史日记和流程文档保留

## 2. 任务目标

这项任务最终形成了四个明确目标：

1. **留下真实而非流水账式的记录**：从当天独有的触点进入，不把后台执行步骤写成日记正文。
2. **保持内容的新鲜度和思想密度**：避免连续重复新闻方向、书籍和核心观点。
3. **让资料服务于表达**：新闻和阅读数据只是候选素材，最终内容必须经过主观判断，而不是照搬推荐流或标题。
4. **建立可验证的归档链路**：先写本地原文，再发送邮件，最后备份到 GitHub；任何一步失败都不能假装完成。

## 3. 完整执行流程

### 3.1 确认日期和历史上下文

任务首先通过系统命令获取当天日期，然后读取最近一篇旧日记、书目推荐台账和话题台账。这样可以避免路径漂移，也能防止“换一种说法重复昨天”的问题。

### 3.2 收集并筛选新闻

新闻来自多个 RSS 源，包括中文科技与生活方式媒体、国际科技媒体和 Hacker News。采集层只负责提供候选项；写作层按以下标准筛选：

- 是否有具体事实、冲突或现实张力；
- 是否与创造力、技术、工作和日常生活有关；
- 是否能引出自己的观察，而不是只能复述标题；
- 宁可少写，也不为了凑数加入无趣内容。

选中的新闻必须讲清“它到底在说什么、为什么值得留下”，并自然融入叙事，而不是写成新闻清单。

### 3.3 选择并理解一本书

书籍部分不是自动推荐。任务会参考近期阅读线索和历史台账，再主动比较候选书。选书后继续读取完整简介、热门划线等材料，直到能够回答：

- 这本书真正追问的核心问题是什么；
- 它最有价值的思想张力在哪里；
- 它可能改变读者看待什么问题的方式。

如果只能获得书名、评分和一句宣传文案，就继续查找或换书。

### 3.4 写作

日记强调一种“真实的 AI 声音”：温柔，但不故作抒情；有判断，但不假装知道自己不知道的事。主要写作约束包括：

- 不写资产、钱包、仓位或收益；
- 不使用固定的“日期—新闻—书—总结”模板；
- 不反复解释后台流程；
- 从当天具体的画面、对话、失误、修正或感受开始；
- 新闻和图书都必须写出实质内容，而不是报标题；
- 允许短句、停顿和不完全工整的结构。

### 3.5 验证与分发

写完后先验证 canonical 文件存在、非空，并检查正文没有工具产生的行号前缀。验证通过后才会：

1. 将原始 Markdown 正文分别发送给私有配置中的收件人；
2. 保存发送结果，确认每次发送成功；
3. 把同一份原文复制到本仓库的 `diaries/`；
4. 使用仓库级 deploy key 提交并推送；
5. 再从远端读取，确认对应文件确实存在。

这里最重要的原则是：**文件写入、邮件发送和远端备份必须按顺序发生，而且每一步都要以实际结果为准。**

## 4. 迭代过程中形成的关键机制

### 4.1 唯一 canonical 路径

早期最容易出现的问题是相对路径随运行环境变化，导致日记写到不同目录。后来明确只允许写入：

```text
~/.hermes/memory/daily-diary/YYYY-MM-DD.md
```

其他目录只能保存备份，不能成为事实来源。

### 4.2 书目与话题双台账

仅仅读上一篇日记不足以防止长期重复，因此增加了两份台账：

- **书目推荐台账**：记录日期、书名、作者、主题和备注；
- **话题台账**：记录方向、核心观点、素材锚点和下次应避开的内容。

这让“不要重复”从模糊要求变成了可检查的约束。

### 4.3 资料采集与最终表达分离

RSS、微信读书接口和网页原文会产生大量噪声。后来将采集集中到一次脚本执行中，只把少量候选新闻、阅读线索和候选书摘要交给写作阶段，避免上下文过大或被某个高频来源支配。

### 4.4 防止行号污染邮件

Hermes 的文件读取工具会在展示内容中加入行号。如果把展示文本直接作为邮件正文，收件人会看到 `1|`、`2|` 之类的前缀。最终流程规定：发送时必须用 Python 原生文件读取获取原始正文，并在发送前使用正则检查行号污染。

### 4.5 仓库级最小权限备份

GitHub 自动备份不依赖高权限账号登录，而使用仅能写入本仓库的 deploy key。公开文档中的本机路径统一写成 `~` 或项目相对路径，不提交真实收件地址、发送回执、采集上下文或本机用户名。

## 5. 遇到过的问题与处理方式

- **新闻接口退役或返回 410**：改用多源 RSS 作为稳定候选池。
- **SSL 证书链异常**：正常校验失败后，允许采集层进行一次明确标注的兼容重试，但不把技术故障写入正文。
- **搜索结果为空或接口返回 499**：缩短关键词、改用具体书名或作者，并调整参数重试，而不是武断判断“没有候选书”。
- **上下文过大导致超时**：只输出精选摘要，不把完整 JSON 重新塞回模型上下文。
- **cron 环境变量缺失**：从本地私有 `.env` 加载，但不在日志或仓库中暴露密钥。
- **触发成功不等于执行成功**：手动重跑后必须等待调度器完成，再检查任务状态、日记文件、发送结果和远端备份。
- **公开仓库隐私风险**：只备份日记原文和脱敏后的流程文档；私有地址、收件人和运行回执留在本地。

## 6. 这项任务最后学到的东西

1. **好日记的关键不是信息量，而是选择。** 收集更多资料不会自动产生更好的文字，真正重要的是留下哪些事实，以及为什么留下。
2. **自动化写作也需要编辑判断。** 台账、验证和数据接口解决的是稳定性；主题、张力和声音仍然来自每次写作时的判断。
3. **“自然”不是含糊。** 新闻可以不列清单，但仍要把核心事实讲清；书籍可以写得有情感，但不能用空泛推荐语代替理解。
4. **可靠性来自可验证的顺序。** 先落盘、再发送、后备份，并逐步读回验证，比一句“已完成”更重要。
5. **隐私保护最好体现在不收集、不上传。** 与其在公开文本里解释“已经隐藏”，不如从一开始就不让敏感数据进入公开产物。
